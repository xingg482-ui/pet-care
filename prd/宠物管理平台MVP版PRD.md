# 宠物管理平台 MVP 版 PRD

## 1. 文档说明

本文档为“宠物管理平台”的第一阶段 MVP 需求文档，目标是让一名实习生在 1 个月内可以基于明确范围完成开发。

原始产品愿景包含宠物健康档案、疫苗/驱虫提醒、问诊预约、美容洗护、寄养、商户端、平台管理端、内容社区和云相册等完整能力。考虑到开发周期和实习生能力，本期不直接实现完整平台，而是先完成一个可运行、可演示、可继续扩展的核心业务闭环。

本期定位：

> 单门店宠物服务订单管理系统 MVP

本期重点验证：

```text
客户管理 → 宠物档案 → 服务项目 → 创建预约订单 → 处理订单 → 完成服务
```

## 2. 项目背景

宠物主人在日常养宠过程中，需要管理宠物基础信息、健康信息和各类服务预约。线下宠物门店也需要记录客户、宠物、服务项目和预约订单。当前许多小型宠物服务门店仍通过微信、电话、纸质登记或表格进行管理，容易出现信息分散、订单遗漏、状态不清、客户宠物档案无法沉淀等问题。

本项目第一阶段先建设一个桌面端管理后台，帮助单个宠物服务门店完成客户、宠物、服务项目和预约订单的基础管理，为后续扩展宠物健康档案、提醒、商户端、平台端和用户端打基础。

## 3. 项目目标

### 3.1 第一阶段目标

1. 实现一个可登录的宠物服务门店管理后台。
2. 支持客户信息的新增、编辑、查询、启用和停用。
3. 支持宠物档案的新增、编辑、查询、启用和停用。
4. 支持服务项目的新增、编辑、查询、启用和停用。
5. 支持创建预约订单，并关联客户、宠物和服务项目。
6. 支持订单查询、详情查看和状态流转。
7. 支持首页展示基础统计数据。
8. 形成清晰的数据模型和接口结构，便于后续继续扩展。

### 3.2 非目标

第一阶段不追求完整商业化平台能力，不实现多商户、多门店、在线支付、自动排班、消息推送、社区、云相册等复杂功能。

## 5. 用户痛点

### 5.1 门店侧痛点

1. 客户信息分散在微信、电话记录或纸质表格中，不便查询。
2. 宠物资料缺少统一管理，历史服务记录不易追溯。
3. 服务项目、价格和时长缺少标准化维护。
4. 预约订单状态不清，容易遗漏确认、取消或完成。
5. 订单金额需要人工计算，容易出错。
6. 缺少基础统计数据，难以快速了解门店运营情况。

### 5.2 宠物主人侧痛点

第一阶段不直接面向宠物主人提供独立用户端，但系统需要记录宠物主人相关客户信息，为后续用户端扩展打基础。

## 11. 核心数据模型

### 11.1 Customer 客户

用于记录宠物主人基础信息。

| 字段 | 类型建议 | 说明 | 规则 |
| --- | --- | --- | --- |
| id | Long | 主键 | 自动生成 |
| name | String | 客户姓名 | 必填，最长 50 字 |
| phone | String | 手机号 | 必填，建议唯一 |
| email | String | 邮箱 | 可选 |
| address | String | 地址 | 可选 |
| status | String | 状态 | ENABLED / DISABLED |
| remark | String | 备注 | 可选 |
| createdAt | DateTime | 创建时间 | 自动生成 |
| updatedAt | DateTime | 更新时间 | 自动更新 |

业务规则：

1. 客户姓名和手机号必填。
2. 手机号不允许重复。
3. 客户存在宠物或订单时不做物理删除，只允许停用。
4. 停用客户不能用于创建新订单。

### 11.2 Pet 宠物

用于记录宠物基础档案。

| 字段 | 类型建议 | 说明 | 规则 |
| --- | --- | --- | --- |
| id | Long | 主键 | 自动生成 |
| customerId | Long | 所属客户 ID | 必填 |
| name | String | 宠物名称 | 必填，最长 50 字 |
| species | String | 宠物种类 | 必填，如猫、狗 |
| breed | String | 品种 | 可选 |
| gender | String | 性别 | MALE / FEMALE / UNKNOWN |
| birthday | Date | 生日 | 可选 |
| weight | BigDecimal | 体重 kg | 可选，不能小于 0 |
| sterilized | Boolean | 是否绝育 | 可选 |
| status | String | 状态 | ENABLED / DISABLED |
| remark | String | 备注 | 可选 |
| createdAt | DateTime | 创建时间 | 自动生成 |
| updatedAt | DateTime | 更新时间 | 自动更新 |

业务规则：

1. 一只宠物第一阶段只属于一个客户。
2. 创建宠物前必须先选择客户。
3. 宠物名称和宠物种类必填。
4. 停用宠物不能用于创建新订单。
5. 宠物存在历史订单时不做物理删除，只允许停用。

### 11.3 ServiceItem 服务项目

用于维护门店可提供的服务。

| 字段 | 类型建议 | 说明 | 规则 |
| --- | --- | --- | --- |
| id | Long | 主键 | 自动生成 |
| name | String | 服务名称 | 必填，最长 100 字 |
| category | String | 服务分类 | 必填，如问诊、美容、洗护、寄养 |
| price | BigDecimal | 服务价格 | 必填，不能小于 0 |
| durationMinutes | Integer | 服务时长，单位分钟 | 必填，必须大于 0 |
| status | String | 状态 | ENABLED / DISABLED |
| description | String | 服务说明 | 可选 |
| createdAt | DateTime | 创建时间 | 自动生成 |
| updatedAt | DateTime | 更新时间 | 自动更新 |

业务规则：

1. 服务名称、分类、价格和服务时长必填。
2. 价格不能小于 0。
3. 服务时长必须为正整数。
4. 停用服务不能用于创建新订单。
5. 已经被历史订单使用的服务项目不做物理删除，只允许停用。

### 11.4 ServiceOrder 服务订单

用于记录用户预约服务后生成的订单。

| 字段 | 类型建议 | 说明 | 规则 |
| --- | --- | --- | --- |
| id | Long | 主键 | 自动生成 |
| orderNo | String | 订单号 | 必填，唯一 |
| customerId | Long | 客户 ID | 必填 |
| petId | Long | 宠物 ID | 必填 |
| appointmentTime | DateTime | 预约时间 | 必填，需晚于当前时间 |
| status | String | 订单状态 | PENDING / CONFIRMED / REJECTED / CANCELLED / IN_SERVICE / COMPLETED |
| totalAmount | BigDecimal | 订单总金额 | 根据订单明细自动计算 |
| remark | String | 备注 | 可选 |
| createdAt | DateTime | 创建时间 | 自动生成 |
| updatedAt | DateTime | 更新时间 | 自动更新 |

业务规则：

1. 创建订单时必须选择客户、宠物、预约时间和至少一个服务项目。
2. 宠物必须属于所选客户。
3. 预约时间必须晚于当前时间。
4. 创建订单后默认状态为待确认 PENDING。
5. 总金额等于全部订单明细小计之和。
6. 历史订单不允许物理删除，错误订单通过取消处理。

### 11.5 ServiceOrderItem 订单明细

用于记录订单中包含的服务项目。

| 字段 | 类型建议 | 说明 | 规则 |
| --- | --- | --- | --- |
| id | Long | 主键 | 自动生成 |
| orderId | Long | 订单 ID | 必填 |
| serviceItemId | Long | 服务项目 ID | 必填 |
| serviceName | String | 服务名称快照 | 创建订单时保存 |
| unitPrice | BigDecimal | 单价快照 | 创建订单时保存 |
| quantity | Integer | 数量 | 第一阶段默认为 1 |
| subtotal | BigDecimal | 小计 | unitPrice × quantity |

业务规则：

1. 创建订单时保存服务名称和价格快照。
2. 后续修改服务项目价格，不影响历史订单金额。
3. 第一阶段不支持手动改价。
4. 第一阶段每个服务数量默认为 1。

### 11.6 OrderStatusLog 订单状态记录

用于记录订单状态变化历史。

| 字段 | 类型建议 | 说明 | 规则 |

| orderId | Long | 订单 ID | 必填 |

## 12. 订单状态流转

订单状态统一使用以下枚举：

| 状态 | 英文值 | 说明 |
| --- | --- | --- |
| 待确认 | PENDING | 订单已创建，等待门店确认 |
| 已确认 | CONFIRMED | 门店已确认预约 |
| 已拒绝 | REJECTED | 门店拒绝预约 |
| 已取消 | CANCELLED | 订单已取消 |
| 服务中 | IN_SERVICE | 宠物正在接受服务 |
| 已完成 | COMPLETED | 服务完成 |

状态流转规则：

```text
待确认 PENDING
    ├─ 确认 → 已确认 CONFIRMED
    ├─ 拒绝 → 已拒绝 REJECTED
    └─ 取消 → 已取消 CANCELLED

已确认 CONFIRMED
    ├─ 开始服务 → 服务中 IN_SERVICE
    └─ 取消 → 已取消 CANCELLED

服务中 IN_SERVICE
    └─ 完成服务 → 已完成 COMPLETED
```

补充规则：

1. 已拒绝、已取消、已完成为结束状态。
2. 结束状态不能继续修改状态。
3. 待确认和已确认订单可以修改预约时间。
4. 服务中、已完成、已拒绝、已取消订单不能修改预约时间。
5. 每次状态变化都需要写入订单状态记录。
6. 第一阶段不做自动排班冲突检测，由门店人工确认预约是否可接收。

## 15. 接口约定

### 15.1 通用分页参数

| 参数 | 说明 | 默认值 |
| --- | --- | --- |
| page | 当前页码 | 1 |
| pageSize | 每页数量 | 10 |

### 15.2 通用状态

客户、宠物、服务项目使用统一状态：

| 状态 | 英文值 | 说明 |
| --- | --- | --- |
| 启用 | ENABLED | 可用于新业务 |
| 停用 | DISABLED | 不可用于新业务，但历史数据保留 |

### 15.3 通用时间字段

所有创建时间和更新时间统一使用：

```text
yyyy-MM-dd HH:mm:ss
```

### 15.4 通用校验

1. 必填字段为空时，接口返回明确错误提示。
2. 数据不存在时，接口返回明确错误提示。
3. 状态不允许流转时，接口返回明确错误提示。
4. 金额、体重、服务时长等数字字段不能为非法值。

## 16. 非功能需求

### 16.1 易用性

1. 后台页面布局保持统一。
2. 列表页需要支持查询、分页和操作按钮。
3. 表单必填项需有校验提示。
4. 新增、修改、状态变更成功后需给出提示。
5. 删除类操作第一阶段改为停用，减少误操作风险。

### 16.2 性能

1. 常规列表查询响应时间应尽量控制在 2 秒以内。
2. 首页统计响应时间应尽量控制在 2 秒以内。
3. 第一阶段数据量按小型门店规模设计，不要求高并发。

### 16.3 安全

1. 登录接口需校验用户名和密码。
2. 未登录用户不能访问后台页面。
3. 不在前端明文暴露敏感配置。
4. 后端接口需进行必要参数校验。

### 16.4 可靠性

1. 创建订单时，订单主表和订单明细需保持一致。
2. 修改订单状态时，订单状态和状态记录需保持一致。
3. 订单金额需由后端计算，不能只依赖前端传值。
4. 历史订单原则上不允许物理删除。

### 16.5 可扩展性

1. 数据模型需为后续健康记录、提醒、商户和用户端扩展保留空间。
2. 服务项目分类可以先用字符串，后续可扩展为字典表。
3. 第一阶段不做复杂权限，但接口和页面结构应避免与未来权限体系冲突。

## 18. 验收标准

### 18.1 基础验收

1. 管理员可以登录系统。
2. 首页可以展示基础统计数据。
3. 可以新增、编辑、查询、启用和停用客户。
4. 可以新增、编辑、查询、启用和停用宠物。
5. 宠物必须关联客户。
6. 可以新增、编辑、查询、启用和停用服务项目。
7. 可以创建预约订单。
8. 创建订单时可以选择客户、该客户名下宠物和服务项目。
9. 订单金额可以根据服务项目自动计算。
10. 可以查看订单列表和订单详情。
11. 可以按照规则修改订单状态。
12. 订单状态变化可以记录日志。

### 18.2 业务验收

1. 停用客户不能创建新订单。
2. 停用宠物不能创建新订单。
3. 停用服务项目不能创建新订单。
4. 预约时间不能早于当前时间。
5. 已取消、已拒绝、已完成订单不能继续修改状态。
6. 服务项目价格修改后，不影响历史订单金额。

### 18.3 文档验收

1. 项目需提供 README。
2. README 需包含启动方式。
3. README 需包含数据库初始化方式。
4. README 需包含预置登录账号。
